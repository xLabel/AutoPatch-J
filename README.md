## 自动修复难在哪

静态扫描器提供的是规则、位置和问题描述，自动修复还需要解决这些问题：

- **信息怎么给：** 正确修复可能依赖类型定义、调用关系和测试。信息太少会误判，把整个仓库交给 LLM 又会引入噪声，需要按任务逐层补充。
- **修改怎么落地：** LLM 只能提出修改，真正作用于仓库需要受控工具。补丁需要有明确的问题依据，绑定当前源码基线，并限制实际写入范围。
- **执行怎么推进：** 修复不是一次问答，需要判断信息是否充分、调用工具、生成补丁并检查结果。一次修复也可能需要同时修改导入、辅助方法和调用方。
- **哪些内容需要被记住：** 扫描结果、待审补丁和审核状态需要独立保存；代码风格、提交规范等工程偏好可以跨任务复用，项目会话历史、正式规范与长期笔记各有职责，需要按当前任务共同使用。
- **结果由谁验收：** 不能由 LLM 自己宣布完成。扫描器、编译、测试或团队规则提供独立证据；证据不足时继续补充、修正或停止。

## 如何稳定交付

> **Agent = LLM + Harness Engineering**
>
> LLM 负责理解代码，Harness Engineering 保障交付质量。
>

真实工程实践：

- **上下文管理：** 从用户目标与当前源码出发，按需读取关联方法、类型、文件及适用项目规范。读取范围与写权限分别控制，关联分析不会自动扩大修改范围。
- **工具系统：** 由 Pydantic AI 承担 Agent 循环、协议、流处理和参数纠错。项目工具负责扫描取证与补丁提案；多段替换按顺序唯一匹配，跨文件修改作为一项完整修复供人审核。
- **执行编排：** 先判断问题是否成立，再决定修改、补充证据或保留现状。一次处理一项完整提案，支持解释和修订；用户批准写范围、审核 diff，最后明确应用补丁。
- **状态与记忆：** 任务、提案与写入事实独立于模型对话保存。项目问答和修复共享会话，用户确认的长期知识保存在项目笔记中，临时修复要求随任务结束清理。
- **评估与观测：** 展示完整 diff 和 Java 语法结果；有扫描依据的提案应用后复扫目标规则。明确区分“源码已写入”“规则未再触发”和尚未执行的编译、测试、业务验收。
- **约束与恢复：** 应用前核对全部文件的当前基线，过期提案须重新准备和审核。跨文件写入失败时停止，准确展示部分应用事实；重启后先人工核查，不自动回滚或重放。

## 工程效能与未来展望

当 AutoPatch-J 进入 CI/CD 流水线，代码扫描不再止于发现问题，修复结果将以可评审的 MR/PR 交付。代码修复也从零散的人工作业，变成随流水线持续运行、可跨项目复用的工程能力。

未来还计划接入 PMD、SpotBugs、Checkstyle 等 Java 工具，扩展独立检查与验收能力。
