# AutoPatch-J 工程指南

设计、修改或审查本仓库代码及工程约束时，按本页核对相关要求。用户问题、已确认行为和实际影响决定方案；当前文件、类、框架及测试只提供调查依据。产品行为与接口统一见 [SPEC](SPEC.md)，授权、验证命令与交付见 [AGENTS](../AGENTS.md)，独立复核操作见 [AI_REVIEW](AI_REVIEW.md)。

Python 语言、排版、命名、docstring 及类型检查遵循 [Python 规范](PYTHON_STYLE.md)，按任务阅读其中链接的 Google 原文；本页维护通用工程判断。检查工具通过不能替代需求、职责、生命周期和测试依据的核对。

## 1. 需求与依据

- 先明确用户要解决的问题、使用场景、改前与改后行为、范围和成功标准，再选实现。区分完成当前目标所必需与可独立延期的工作，说明取舍；不得借延期省略必要交付、安全保护或验证。简单任务可以简述，不强制另写需求文档、计划或表单。
- 沿相关输入、数据来源、调用链、完整输出及必要 Git 历史调查，区分当前事实、已确认需求、建议和待验证假设。不凭孤立片段判断，不把旧代码、旧测试或历史通过记录升级为需求。
- 保留原始名称、字段、默认行为、条件和例外的含义，不因改写术语或自行补默认值改变要求。代码或测试与需求冲突时，先核对依据，修正错误的一方；受到质疑时重新核对原始要求，不为已有实现补造理由。
- 可查明的事实定向查证，影响方案的技术疑点查相关实现和必要官方资料；产品偏好或取舍及时澄清。外部实践结合本项目场景判断，来源可靠不等于方案适用。依据充分即推进，不扩为无关全仓审计；只有部分工作依赖未决事项时，其余已授权工作继续。

例如，目标是修复 Java finding 时，应核对从扫描取证、草案、人工审核、源码写入到验证反馈的用户可见结果。仅生成 diff 或让工具返回成功，不能证明[补丁闭环](SPEC.md#5-补丁安全与人工审核)成立；CI/CD 愿景也不自动变成本次交付范围。

## 2. 设计取舍与复用

- 新增相似功能或重构前，核对项目、标准库、SDK、框架和成熟组件的实际能力。在本项目已确认边界内能满足同一需求时复用，只补已查明的具体缺口；职责或失败语义不同的逻辑可以独立，不为几行局部逻辑强加依赖。
- 新增抽象、状态、缓存、重试、恢复或依赖，说明实际问题、简单做法为何不足、收益是否值得维护成本。说明深度随影响而定，不新增固定审批或表单；不得仅因“可能有用”预建机制。
- 既有模式仅在适合当前需求时沿用。模块、类、文件组织和框架选择可以调整，已有机制按实际调用与用途取舍，不因存在永久保留，也不为简化删除必要校验、数据保护或恢复。改变已确认行为须说明差异，按 AGENTS 的授权边界对齐。
- 正确性、语义清晰和维护性优先。文件、行数、分支或告警减少不能单独证明改进；不为统一形式增加公共层、基类、只转发调用的包装或万能协调器，也不借格式、命名或告警处理改变业务行为。

例如，增加 LLM 重试前先核对[请求与上下文额度](SPEC.md#62-请求额度上下文与正常结束)：SDK 网络 retry、工具参数纠错和摘要调用的触发不同，但都影响总成本；不要重放已经消费的流或已产生副作用的工具流程，也不再套一层笼统重试器。

## 3. 职责、类型与命名

- 业务判断、状态所有权与提交责任明确，调用入口经过责任组件，调用方不复制其核心规则。流程编排、工具适配、持久化与终端展示按职责协作；相同规则集中维护，前提、顺序或失败语义不同的行为不强行合并。
- 稳定的跨组件业务输入、结果和快照使用明确类型及具名字段，不用万能字典、`Any` 或位置元组掩盖已知业务结构。外部原始 JSON、SDK wire、第三方固定接口和简单局部数据保留适合的表示，不机械为每个值新增模型；在所属边界完成必要校验，类型断言不能代替运行时校验。
- 名称在调用处表达对象、动作、结果和必要单位，区分读取、请求、校验、保存及实际完成。类型表达数据，变量表达职责；有明确语境的局部惯用名可保留，不机械增加前后缀、缩写或反复改名。
- 职责变化同步核对定义、导入、调用参数、接收变量，以及测试、维护工具和文档中的相关调用。沿调用链只在职责或内容变化时改名，不只改定义留下误导性旧名；对外字段遵守已确认契约。注释和文档字符串解释非显然条件、取舍与限制，避免复述代码。

例如，finding 句柄、规则 ID、scan ID 和审核项 ID 具有不同职责，不能因都叫 ID 合并；草案暂存、审核工作台、实际写入及验证结论也不能混成一个“成功”状态。当前[架构导航](SPEC.md#1-产品能力与架构)用于定位，不冻结内部组件名称或数量。

## 4. 校验、异常与生命周期

- 按信任边界、状态变化和失败后果分配校验，优先复用框架及责任组件能力。新增限制说明目的、依据及对合法输入的影响，不因“更严格”缩小合法范围；条件相似时先确认用途和状态是否相同，再判断重复。
- 异常捕获须承担具体的转换、恢复、清理或展示责任；无需处理的异常交适当上层，不层层捕获、重复记录或仅为统一形式打印堆栈。不吞掉编程错误，不把失败改成空结果或成功；降级须符合所属业务契约。
- 保留主错误和必要结果，次生收尾错误不得掩盖主业务失败。诊断在掌握事实的位置记录，并遵守 [LLM 与 Memory 诊断边界](SPEC.md#63-诊断边界)，不因 debug 或通用日志机制扩大可保存内容。
- 按实际影响核对状态提交与回滚、事务范围、连接与文件、后台任务、异步交叠、取消及退出收尾。复用前确认实例和资源生命周期适合调用语境，不为理论可能性扩建无关恢复框架。

本项目中，工具白名单、focus/path 隔离、finding 绑定和 apply 前重读分别约束调用权限、目标范围、证据身份及当前源码状态，不能当作同一种重复校验删除。具体行为见[源码与权限](SPEC.md#3-源码工具与任务权限)及[补丁安全](SPEC.md#5-补丁安全与人工审核)。

失败处理同样按业务区分：[扫描失败](SPEC.md#4-扫描与有界审计)不能冒充零 finding；[Memory 存储不可用](SPEC.md#63-诊断边界)按契约提示并隔离，不能一概吞掉 contract 或编程错误；[会话保存失败](SPEC.md#71-普通会话)不能抹去已经生成的回答或覆盖并发修改。不能用统一兜底抹平这些区别。

## 5. 测试、审查与自检

- 业务预期取自原始需求、项目契约和适用协议。不能从既有测试、mock 或快照反推业务需求，也不能为通过断言扭曲业务代码；实现不能生成自己的预期，再用二者一致自证正确。允许根据已确认需求先写测试。
- 旧测试与实现都可能有错。出现冲突时定向核对来源与行为，修正错误的一方；不得通过修改需求、文档、放宽断言、跳过必要用例或宽松替身为错误实现背书。正确地变更测试预期须有需求依据。
- 替身模拟外部边界、固定输入与故障场景，不替被测业务作出成功判断；按测试目标保留实际判断、状态转换或持久化组件。聚焦断言核对有意义的完整结果，不以个别字段存在、配置写入或程序能启动代替目标行为；不为覆盖数量机械增测。
- 对照原始目标及获批方案核对实际入口、输入、处理、完整输出、必要副作用、失败恢复和资源生命周期；涉及交互时核对用户实际操作及反馈。按影响选择聚焦验证，命令及真实 LLM 授权见 [AGENTS](../AGENTS.md#实现与验证)。静态检查、运行验证、视觉检查与人工验收各有证据范围，测试通过不证明需求全部成立。
- 确认问题后，定向检查本任务范围内同根因关联问题，在已有授权内处理；更广架构调整另行对齐。问题给出位置、可达触发、影响、证据及最小修正方向，结合修复价值和成本判断；理论可能性本身不足以认定缺陷，已确认取舍无新反证不反复报错。区分确认问题、疑点、限制与可选改善，允许无发现。
- 主助手先完成上述自检、必要修正和适用验证，再进入[独立复核](AI_REVIEW.md#1-自检对象与阶段选择)。按本次任务核对相关要求，不为每次改动重审全仓；如实区分通过、失败、跳过和未验证，不用计划、文档修正或前序成绩冒充本次运行结果。

例如，测试[补丁验证](SPEC.md#53-应用后验证)时，扫描器替身提供复扫证据，目标是否消失由实际 verifier 判断；测试[普通会话与项目笔记](SPEC.md#7-项目-memory)时，核对重启恢复、项目隔离、实际 SQLite 内容和版本冲突，不能用导出文件存在代替持久消息和笔记的正确性。仅测试替身返回成功不能验证这些业务。
